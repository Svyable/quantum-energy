# R2 Facility Dry-Run Packet v3.30

## Purpose

This increment tests **packet interoperability**, not physics. It verifies that the merged v3.27 facility capability/evidence contract can be represented as a complete, integrity-checked packet before any real facility response or measurement is accepted.

A `STRUCTURAL_PASS` is therefore a **synthetic/software-verification result only**. It does not establish real facility capability, metrology validity, R2 device performance, electron–phonon coupling, open-quantum transport, or commercial photovoltaic performance.

## Provenance

Canonical input: `technical/data/r2_facility_capability_contract_v3_27.json` on `main`, checked 2026-08-27.

## Quantitative contract

Let:

- `C = 7` = number of v3.27 required capability classes;
- `E_c` = set of evidence roles attached to capability `c`;
- `E = union_c E_c`;
- `A` = administrative packet roles not attached to one capability.

From v3.27:

- `|E| = 13` unique capability evidence roles;
- `A = {analysis_freeze_record, packet_manifest}` so `|A| = 2`;
- total required packet roles `R = |E| + |A| = 13 + 2 = 15`.

These are dimensionless finite-set counts. The executable validator independently reads `required_packet_roles` and separately reconstructs the union of capability evidence roles. Exact set/count agreement is required; tolerance is zero roles.

## Manifest contract

Each v3.27 role appears exactly once with:

- `role`;
- safe relative path;
- SHA-256 digest;
- byte count;
- evidence state;
- provenance note.

Evidence states:

- `SYNTHETIC_PLACEHOLDER` — generated solely to test packaging/software;
- `REAL_EVIDENCE` — reserved for a source object actually supplied with provenance;
- `MISSING` — required role not yet supplied.

The blank CSV template starts every role as `MISSING`. No absent object is silently converted to zero uncertainty or a favorable status.

## Status semantics

- `STRUCTURAL_PASS`: all 15 v3.27 roles are represented exactly once, paths are safe, bytes and hashes agree, and evidence states/provenance are valid. **Not a scientific PASS.**
- `FAIL`: evidence is present but integrity, uniqueness, path-safety, or claim-boundary rules are violated.
- `INCOMPLETE`: one or more required roles/provenance fields are absent.

The dry-run vocabulary deliberately does not contain plain `PASS`, `SCIENTIFIC_PASS`, or `FACILITY_PASS`.

## Integrity / independent checks

`tools/validate_r2_facility_dryrun_v3_30.py --self-test` deterministically creates an isolated synthetic packet and requires:

1. complete synthetic packet -> `STRUCTURAL_PASS`;
2. one missing required role -> `INCOMPLETE`;
3. one byte mutation after manifest creation -> `FAIL`;
4. duplicated role -> `FAIL`;
5. `../` path traversal -> `FAIL`;
6. complete synthetic packet is never reported as plain scientific `PASS`.

SHA-256 and byte counts are evaluated from the actual generated bytes. The synthetic generator is deterministic and uses no random numbers, so stochastic seed/convergence checks do not apply.

## Limiting cases

- Zero missing roles with valid integrity can only reach `STRUCTURAL_PASS`, never a scientific result.
- One missing material role keeps the packet `INCOMPLETE` regardless of how many other roles are present.
- One integrity contradiction dominates completeness and returns `FAIL`.
- A role count other than exactly 15 indicates schema drift or malformed packaging and cannot pass.

## Uncertainty and sensitivity

The dominant uncertainty at this stage is epistemic: whether a real facility can provide a valid object for each role under one frozen configuration. It is represented categorically as `MISSING` rather than assigned a probability.

Sensitivity is non-compensatory. Fourteen valid roles do not compensate for one missing decision-critical role. This is intentional because downstream gate dependencies can be invalidated by a single missing prerequisite.

No measurement uncertainty is estimated in v3.30.

## Statistical independence

This increment performs no device-level statistical inference. Packet objects and manifest rows are not experimental replicates.

The inherited hierarchy remains:

`lot -> substrate -> device/pixel -> session -> sweep or step replicate -> measurement`.

A later multi-facility campaign must add facility/configuration as an explicit factor before treating measurements as exchangeable.

## Conventional/null explanation

A facility can produce a perfectly formatted packet while its measurements are scientifically inadequate. Conversely, a capable facility may initially fail packaging because of export/provenance incompatibility.

Therefore structural packet success is only an interoperability discriminator. Scientific gates must still evaluate the real measurements under their frozen criteria.

## Safety / environment

No experiment, sample shipment, fabrication, optical exposure, or electrical condition is authorized by this software test. Facility EHS, source-duty, electrical, thermal, shipping, interlock, and instrument-rating rules remain controlling for any real packet.

## Kill / narrow gates

- If the 15-role packet cannot be produced without manual undocumented transformations, narrow the facility-integration claim and build a versioned adapter before real acquisition.
- If a real packet is missing a material role, preserve `INCOMPLETE` rather than estimating or inventing it.
- If bytes or hashes disagree, preserve `FAIL` and investigate provenance before analysis.
- Never use `STRUCTURAL_PASS` as evidence for mechanism or performance.

## Single best next increment

After human review of the frozen questionnaire in #21, run this exact dry-run interface on the first returned candidate response: require the candidate to supply a small non-scientific/example packet for all roles it claims it can return, preserve unavailable roles as `MISSING`, and resolve export/provenance incompatibilities before scheduling real R2 measurements.
